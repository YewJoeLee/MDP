# Android Remote Controller Requirements and Progress

Last reviewed: 28 August 2026  
Branch reviewed: `appV1`  
Implementation commit reviewed: `e17c11a` (+ uncommitted receive-loop, movement, and UI-layout fixes, see C.1/C.3/C.4)

This document translates the supplied MDP material into an Android-focused work tracker. The PDFs remain the authoritative assessment documents. Statuses below describe the current code and the verification evidence available in this repository; an item is not considered assessment-ready until it has been demonstrated with the AMD Tool or the team robot and signed on the checklist.

## Status legend

- **Implemented - evidence pending:** the Android code covers the requirement, but a live Bluetooth/robot demonstration is still required.
- **Implemented - integration pending:** the feature exists, but the team must confirm the protocol, coordinate convention, or hardware behavior.
- **Partial / follow-up needed:** the main feature exists, but a known detail still needs correction or confirmation.
- **Conditional team item:** it comes from the general MDP briefing rather than the ARCM checklist and applies only if Android is used for that team deliverable.

## AMD Tool integration notes (from `AMDTOOL User Guide.pdf`, reviewed 28 Aug)

1. **Connection direction (C.2/C.8 — code fix applied).** The guide's main walkthrough ("Connect to Bluetooth Device (As client)", 5 slides with screenshots) has the *AMD Tool* scan for and dial into the Android tablet — i.e. the tool is the Bluetooth client and the phone/tablet must be a Bluetooth **server**. The app previously only dialed out (`createRfcommSocketToServiceRecord`), so it had no way to accept an incoming connection from the tool in that mode. `BluetoothController` now also runs a background `listenUsingRfcommWithServiceRecord` accept-loop at all times, so the app works as *either* the client (our own Scan/Connect UI, confirmed as a valid alternative by the C.2 checklist-clearing slide's "The software can act as Bluetooth server" note) or the server (AMD Tool dials in). This also directly benefits C.8: the AMD Tool's own reconnect test ("Disconnect" then "Reconnect to last device" from its Bluetooth menu) is *it* redialing in, which only an open server socket can accept.
2. **Command string mismatch (C.3 — resolved 28 Aug, code changed).** The AMD Tool's virtual robot and Command Log only react to whatever strings are configured under Settings → Received Commands, and its *defaults* are single/short tokens: `f` (forward), `r` (reverse), `tl` (rotate left), `tr` (rotate right), `sl`/`sr` (strafe), `beginExplore`, `beginFastest`, `sendArena`. The app's movement buttons previously sent `MOVE,F` / `MOVE,B` / `MOVE,L` / `MOVE,R`, which a *default-configured* AMD Tool would not recognise, making a C.3 demo look broken even though the app was transmitting correctly. The app now sends `f`/`r`/`tl`/`tr` directly (both over Bluetooth and to `moveRobot`'s local map-update logic), so no AMD Tool reconfiguration is needed before demoing. `STOP` is unchanged (no AMD Tool default exists for it; the virtual robot just won't react, which is fine). The Robot Status Demo button still sends JSON (`{"status":"exploring"}`, ...) by default rather than this app's `MSG,...` format — that one is unresolved, see "Integration decisions still needed" below.
3. **The guide's own "Clearing checklist" slides (pages 18-26) use a different item numbering than our official checklist** (`androidCheck.pdf`, C.1-C.10) and include a few items — "Manual/Auto map update buttons" (its C.7) and "two persistent reconfigurable F1/F2 command buttons" (its C.8) — that do not appear in our actual C.1-C.10 spec at all. These look like carryovers from a different assessment year's checklist bundled into the same generic tool guide. Treat the tool guide as *how to operate the tool*, not as an additional source of requirements — do not add UI for those two items unless the current-year checklist is confirmed to include them.

## Assessment and evidence checklist

The general briefing states that system functionality is a 20% group assessment, the supervisor signs demonstrated checklist items, and contributor names should be recorded for each component. The supplied briefing gives the system checklist deadline as Friday 5:00 pm of Week 7. It also lists an Android-related individual quiz in Week 7, an image-recognition task in Week 8, a fastest-robot task in Week 9, and a maximum-five-minute video due in Week 10.

For the Android contribution, prepare evidence for:

- Bluetooth permissions, scanning, device selection, connection, and bidirectional text transfer.
- Movement commands demonstrated through the AMD Tool or the real robot.
- A selective status message received from the robot.
- At least two obstacles added/moved/removed, including the Bluetooth messages produced.
- One face annotation, its changed appearance, and the outgoing message.
- A `TARGET` update with and without a face.
- `ROBOT` updates for multiple positions and directions.
- A temporary disconnect followed by successful automatic reconnection.
- Your name entered as contributor for the Android checklist items you completed.

## Integration decisions still needed

1. **Movement protocol:** the app now sends `f`/`r`/`tl`/`tr` (matching the AMD Tool's default Received Commands, so no tool reconfiguration is needed for the C.3 demo — see "AMD Tool integration notes" above) plus `STOP`. Still confirm with the robot/RPi team that the *real robot* parses these same short strings, or swap them for whatever the team agrees on.
8. **Bluetooth connection direction:** the app now supports both directions (dials out via Scan/Connect, and listens as a server in the background) so it works whether the AMD Tool or the real robot side initiates the connection. Confirm which direction the robot side actually uses.
2. **Obstacle protocol:** confirm `ADD,B1,(x,y)` and `SUB,B1` and whether coordinates are zero-based.
3. **Face protocol:** confirm the current `FACE,B1,N,(x,y)` format. The ARCM slide shows `FACE,B2,N`, while the formal checklist additionally requires the obstacle coordinate.
4. **Incoming protocol:** the app no longer requires a trailing newline to deliver a received message (see C.1 fix), but if the robot/RPi can send two messages back-to-back without a newline between them, they may arrive concatenated in one read and get misparsed. Confirm whether the team's protocol will use newline termination consistently, and whether `TARGET` face direction is always included.
5. **Map dimensions/convention:** the arena is now configured as 20×20 with valid x/y indices `0..19`; confirm the origin, y-axis direction, and whether obstacles occupy one grid cell.
6. **Image verification:** decide whether the stitched RAW image display belongs in Android or on the PC side.
7. **Bluetooth hardware:** confirm that the target is classic Bluetooth SPP. The current implementation is not a BLE GATT client.

## Overall conclusion

The current app covers the functional shape of all ten ARCM checklist items. No checklist item is clearly absent from the Android code. The map is configured for the required 20x20 arena with indices `0..19`, but the coordinate convention and all Bluetooth message formats still need final team agreement. C.1-C.4 and C.6-C.10 still need live AMD Tool/robot demonstrations. Both mandatory task assessments also require cross-subsystem integration; the Android app can monitor and control the agreed interface, but it does not implement the robot’s autonomous movement or image-recognition algorithms. The stitched RAW image viewer is the only notable Android feature not present, and it is conditional on the team choosing Android for that general MDP verification requirement.
